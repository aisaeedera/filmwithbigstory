### 3.2 Data Layer

```

  packages.ts                 — Silver/Gold/Platinum package definitions (from QA-approved export)
  addons.ts                   — Released add-ons with pricing states
  guest-screens.ts            — Screen sizes and pricing states
  lanes.ts                    — Lane definitions (male active, female/aqd coming soon)
  terms.ts                    — 60-day cloud, YouTube retention, cancellation terms
```

**CRITICAL: Pricing Data Consumption Rules**
- The website MUST consume only the QA-approved client-safe pricing export
- NEVER hand-type prices into the codebase
- The export format is JSON, generated by the pricing toolchain at `wedding-proposal-system/scripts/wedding_pricing_toolchain.py`
- The export carries: source workbook version, SHA-256, generated timestamp, release/approval state
- Only client-safe released rules — NO internal costs, margins, supplier notes, or HOLD inputs
- The website must NOT read the XLSX for every live request
- The website must NOT maintain an independently typed price list

**Data flow:**
```
Approved Excel source model
    ↓ recalculation + dual-view QA (LibreOffice)
Versioned client-safe pricing export (JSON)
    ↓ consumed at build time
src/data/wedding-quotation/*.ts (typed constants)
    ↓
WeddingQuotationWizard components
```

### 4.6 OTP Gate

**Flow:**
1. Client browses and configures anonymously (Steps 1–4)
2. Before detailed line-item prices, totals, or quotation summary:
   - Enter name
   - Verify mobile number by OTP
3. Verified identity linked to saved configuration
4. After OTP: prices revealed, quotation summary shown

**OTP Requirements:**
- Expiring one-time codes
- Rate limits and abuse protection
- Minimal retained personal data
- Approved privacy notice and consent language
- No internal cost/margin exposure
- OTP does NOT confirm availability, price approval, payment, or booking

**Provider:** TBD — needs Saeed decision (Twilio Verify, Vonage, or custom)

### 4.7 Review Before Payment/Booking

- After configuration + OTP, client sees controlled quotation summary
- Summary shows: selected package, all inclusions, add-ons, terms
- Client submits configuration to Big Story for review
- NO automatic payment, NO automatic booking
- Big Story verifies: date/supplier availability, venue feasibility, true cost/margin, crew capacity, Price Confirmation Required items
- Only after Big Story approval may payment/booking be offered

## 7. Technical Architecture Notes

### 7.1 State Management

The multi-step wizard needs client-side state for:
- Selected lane (male/female/aqd)
- Event details (date, venue, city, headcount)
- Selected package (Silver/Gold/Platinum)
- Customizations (extra hours, add-ons, guest screens)
- OTP verification state (verified name + mobile)
- Submission state

**Recommendation:** React `useReducer` or Zustand (if already in the project). Check `package.json` for existing state management.

### 7.2 Form Handling

- The existing `ContactWizard.tsx` component provides a multi-step form pattern
- The existing `ContactForm.tsx` and `MediaInquiryForm.tsx` provide form submission patterns
- Server actions at `src/app/actions.ts` handle form submissions
- The configurator should use Next.js server actions for OTP verification and submission

### 7.3 Analytics

- PostHog is already integrated (`src/lib/analytics.ts`)
- Track: step completion, package interest, disabled Coming Soon interactions, OTP conversion, submission outcome
- Do NOT expose client-identifying information or OTP values in analytics

### 7.4 SEO / Schema

- `serviceSchema` for the configurator page
- `breadcrumbSchema` for navigation
- `faqSchema` for wedding quotation FAQs
- `noindex` on the configurator itself (it's a conversion tool, not a content page)

### 7.5 i18n

- Full bilingual support (EN/AR)
- All copy in `L` format: `{ en: "...", ar: "..." }`
- RTL support via existing `[locale]` layout
- Date formatting per locale
